# 情報システムハードウェア規模算定指針 (TTAK.KO-10.0292/R3)

## 1. 概要

### A. 定義
> 情報システム構築時に、サーバ・ストレージ・ネットワークなどの**ハードウェア容量を業務量と性能指標に基づいて客観的・定量的に算定**するためのTTA標準指針(2023.12 R3改訂)。

規模算定(Sizing)とは、「どの程度の性能の機器をどれだけ揃えるべきか」を**根拠をもって**決定する活動である。経験やベンダー提案だけに依存すると判断の責任の所在が不明確になるが、本指針は共通の計算手順と性能指標(tpmCなど)を標準化することで、異なる事業者・監理者・発注機関が**同じ方法で検証可能な根拠**を作れるようにする。

### B. 登場背景および必要性
ハードウェア算定は両方向に失敗する。**過大算定**は必要以上の機器を購入して予算と床面積・電力を浪費し、**過小算定**はピーク時の性能低下・障害につながりサービスの信頼を損なう。特に国民の税金が投入される**公共・大規模事業**では、「なぜこれだけの機器が必要なのか」を監理および予算審議の過程で客観的に説明しなければならない。標準指針はこの説明を可能にする共通の物差しとして、算定結果の妥当性を事後に検証できるようにする。

### C. 規模算定の対象
算定対象は**サーバ(WAS/DB/AP)**、**ストレージ・バックアップ**、**ネットワーク(回線・スイッチ)**、**セキュリティ機器**に区分される。各対象は負荷の性格が異なるため指標も異なり、サーバは処理量(TPS・tpmC)、ストレージはデータ増加量とIOPS、ネットワークは帯域幅を中心に算定する。

## 2. 規模算定の手順

```mermaid
flowchart LR
  A[要求・業務量分析] --> B[算定対象・方式選定]
  B --> C[基準値・補正係数適用]
  C --> D[規模算出]
  D --> E[検証・調整]
```

手順の論理は、**「まず需要を定義し、その需要を機器の単位性能で割る」**というものである。まず**業務量分析**において同時利用者・トランザクション(TPS)・データ量と**ピーク(最大負荷)**の時点を把握する。規模算定は平均ではなくピークに耐えなければならないため、ピークの把握が特に重要である。次に対象ごとの**算定方式**を定め、性能・余裕率・冗長化・目標可用率などの**補正係数**を反映したうえで規模を**算出**し、最後にベンチマーク・妥当性によって**検証・調整**する。

| 段階 | 内容 |
|---|---|
| 業務量分析 | 同時利用者・トランザクション(TPS)・データ量・ピークの把握 |
| 方式選定 | 対象別の算定方式(定量・参照)の決定 |
| 補正適用 | 性能・余裕率・冗長化・可用率係数の反映 |
| 算出・検証 | 規模計算後に妥当性・ベンチマーク検証 |

## 3. 規模算定の方式

算定方式は大きく三つある。**数値(定量)ベース**は、TPC-CのtpmC、TPCのOPS、SPECのSPECintのような**標準性能指標**で計算する方式であり、根拠が明確なため大規模な新規システムに適している。**参照モデルベース**は、類似する既存システムの実測値や標準構成を比較・類推する方式であり、新規の指標算定が困難な場合や検証の補助が必要な場合に用いる。これに**補正・余裕率**を共通に適用し、現実の不確実性を吸収する。

| 方式 | 説明 |
|---|---|
| 数値(定量)ベース | tpmC・OPS・SPECintなどの標準性能指標で計算 |
| 参照モデルベース | 類似システムの事例・標準構成と比較して類推 |
| 補正・余裕率 | ピーク率・増加率・冗長化・目標可用性を反映 |

算出式の骨格は、**必要性能 = 基準トランザクション量 × ピーク率 × 余裕率 ÷ 機器単位性能**である。例えば平常時の毎秒処理量を基準とし、ピーク時に負荷が3倍に集中し(ピーク率3)、CPU使用率を70%までに抑えるために30%の余裕(余裕率約1.43)を設けると、実際に確保すべき性能は基準値の4倍を上回ることになる。このように係数を明示的に掛け合わせることで、算定根拠が透明になる。

## 4. 考慮事項

算定は現時点のスナップショットではなく、**将来と障害状況まで**包含しなければならない。今後3〜5年のデータ・利用者の増加を反映しなければ早期に増設が必要となり、冗長化・災害復旧の容量を見落とすと障害時に破綻する。

| 区分 | 内容 |
|---|---|
| ピーク・成長 | ピーク負荷および今後3〜5年の増設余力を反映 |
| 仮想化・クラウド | リソース共有・オートスケール環境の特性を反映 |
| 可用性 | 冗長化(N+1)・災害復旧(DR)容量の確保 |
| 検証 | ベンチマーク(BMT)・負荷試験で算定値を実証 |

## 5. 示唆点
技術士の観点で注目すべき変化は、**クラウド移行**がサイジングのパラダイムを変えつつあるという点である。オンデマンド・オートスケール環境では、ピークに合わせて機器をあらかじめすべて購入する必要はなく、必要なときに増やせばよいため、「ピーク対比の固定確保」から「**弾力的確保 + コスト最適化(FinOps)**」へと重心が移っている。それでも規模算定指針は依然として有効である。オートスケールでも最小・最大容量と予算を定めるには業務量ベースの定量的根拠が必要であり、クラウドコストの予測やリザーブドインスタンスの規模決定もまたサイジングの論理の上に成り立つからである。すなわち指針は、**初期容量・コスト算定の客観的根拠**として、オンプレミス・クラウドを問わず引き続き活用される。

---

> **一言まとめ**: TTAK.KO-10.0292/R3は、*業務量分析→方式選定→補正適用→算出・検証*の手順でHW容量をtpmCなどの性能指標に基づき客観的に算定する標準指針であり、過大・過小算定を防ぎ公共事業の監理根拠を提供するとともに、クラウド時代にも初期容量・コスト算定の基準として有効である。
